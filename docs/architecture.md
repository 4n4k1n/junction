# Architecture

```
Meta Ray-Ban Display ── DAT SDK ── iOS app (ios/)
                                      │ JSON over HTTP (LAN)
                                   FastAPI backend (backend/app)
                                      ├─ build/analyzer        Claude vision: which known parts, what project
                                      ├─ build/facts           hardware/facts/*.json + electrical safety rules
                                      ├─ build/planner         wiring steps, by rules from the database
                                      ├─ build/codegen         Claude writes the sketch; schema, static checks, compile, repair
                                      ├─ build/session_router  guided session state machine (/sessions)
                                      └─ build/router          sketch approval + deploy job queue (/builds)
                                      ▲ polls for approved jobs
                                   Mac deploy agent (agent/) ── USB ── Arduino UNO Q ── KY-037
```

## Components

| Part | Does | Does not |
|---|---|---|
| iOS app | glasses session, renders `display_text`, sends goal / confirm / approve / test result | hold API keys, talk to Claude, talk to the board |
| Backend | owns build state, calls Claude, checks plans against facts, queues deploy jobs | touch hardware |
| Deploy agent | claims approved jobs, verifies the sketch hash, compiles and uploads, reports the log | decide what to flash |
| `hardware/facts` | pin names, voltages, board identifiers, each with source and confidence | contain anything generated |

## State machines

Guided session (`/sessions`):

```
POST /sessions ─▶ awaiting_analysis ─(analyze)─▶ needs_confirmation ─(analyze + confirmed_inventory)─┐
                         │                                                                            ▼
                         ├──────────────── all parts confirmed, plan safe ───────────────────────▶ wiring
                         ├─▶ unsupported   (project outside the MVP parts)                           │ confirm-step × N
                         └─▶ blocked       (plan failed a safety check)                              ▼
                                                                                    wiring_complete
                                                                                                     │ generate
                                                                                                     ▼
                                                                                    code_generated (build_id)
```

Build (`/builds`), created by the session in `awaiting_approval`:

```
awaiting_approval ─(approve + sha256)─▶ approved ─(agent claim)─▶ deploying ─▶ awaiting_test ─▶ done
        │ reject                                                       │ failed            │ failed
        ▼                                                              ▼                   ▼
     rejected                                                        failed              failed
```

Any call in the wrong state returns 409.

## Safety properties (each has a test in `backend/tests/`)

- The vision model can only name parts from the hardware database (closed enum; anything else becomes
  `unknown`). Its prompt contains appearance descriptions only, no pins or voltages.
- An uncertain detection, a failed AI call, or an unreadable answer leads to questions for the user,
  never to a guessed plan.
- Checks on the physical part (KY-037 pin labels) are always asked, whatever the vision confidence.
- Wiring is generated by rules. `check_safety` rejects a signal that can exceed the board pin's limit
  (for example sensor on 5V into any pin, or anything above 3.6 V into D3 or A0-A5), a missing or
  out-of-range supply, and misrouted ground or signal pins.
- A photo review returns `electrically_verified: false` by type and never confirms a step.
- Model text that reaches the sketch (the title, in a comment) is reduced to one line of safe characters.
- Generated code is rejected unless it uses only the approved pins and header and a small polling
  subset of the Arduino API (`codecheck.py`), and it is compiled with the real UNO Q core when the
  toolchain is present. At most two repair requests, then the rule-based template.
- The backend can compile but has no upload code. The agent uploads only with an approval token signed
  when the user approved: bound to the build and the sketch hash, valid 5 minutes, usable once.
- The agent runs only `arduino-cli` with fixed arguments, inside a temp workspace, on 127.0.0.1.
- A deploy job exists only after `/approve`. Before that the agent's claim returns 204.
- Approval names the sketch's sha256. A different hash is a 409, so a regenerated sketch needs a new approval.
- The agent recomputes the hash and refuses to flash a sketch that does not match.
- A plan that names a pin, component or fact missing from `hardware/facts` is rejected (502) and never shown.
- With `LEARNLENS_AGENT_TOKEN` set, agent endpoints need the `X-Agent-Token` header.

## Hardware database

`hardware/facts/uno-q.json` and `ky-037.json`. Each pin has a kind and limits and points at a fact;
each fact has a source and a confidence (`official_doc`, `vendor_doc`, `secondary`, `unverified`).

Checked against the official UNO Q datasheet (SKU ABX00162-ABX00173) and the official core source:

| Fact | Value | Source |
|---|---|---|
| Header logic level | 3.3 V on JDIGITAL and JANALOG | datasheet 9.6 |
| D0-D13 as inputs | 5 V-tolerant, except D3 (3.6 V max) | datasheet 9.6 |
| A0-A5 | not 5 V-tolerant in analog mode, about 3.6 V absolute max | datasheet 9, 9.7 |
| +3V3 pin | 3.1 / 3.3 / 3.5 V (min / typ / max) | datasheet 3.2, 9.7 |
| MCU RGB LEDs | active-low; LED3 red is PH10 | datasheet, LEDs |
| `LED_BUILTIN` | PH10 (first `builtin-led-gpios` entry) | ArduinoCore-zephyr overlay |

The KY-037 has no maker datasheet. Its facts come from Joy-IT's documentation of their module
(`vendor_doc`): LM393 comparator, DO goes high above the threshold, wired to 3.3 V on 3.3 V boards.
Because clones differ, the user must confirm the pin labels, the plan powers the sensor from +3V3 so
no output can exceed 3.5 V, and the sketch reacts to a level change instead of assuming a polarity.

The FQBN `arduino:zephyr:unoq` is confirmed with the installed core 1.1.0. Still to confirm on the
bench: `LED_BUILTIN` actually blinks (a forum thread reports trouble under IDE 2.3.7), how `Monitor`
output is read on the Mac, and the KY-037 behavior at 3.3 V.

## iOS app

See `ios/README.md`. One `DeviceSession` carries both `Display` and, for the moment of a capture,
`Camera`. `GlassesManager` owns the session and the display; `CameraService` borrows the session.
Simulated glasses use MockDeviceKit and the same `addDisplay()` path. Not yet built with Xcode.

## Current limits

- Sessions, builds and jobs are in memory and vanish on backend restart.
- One project shape: a digital sensor event drives the built-in LED (toggle or follow).
- The Claude paths (vision, code generation) are tested with mocked responses only. No live call has
  been made from this Mac.
- Compiling for the UNO Q is verified. Upload, board discovery and log read-back are implemented from
  the core's files but have never run against a board (`agent/README.md`, smoke test).
